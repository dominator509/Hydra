# EP-018 Persisted Vault and Runtime Secret Source

Plan status: COMPLETE

## 1. Purpose / Big Picture
Make Hydra's documented encrypted-vault contract executable and connect it to the real kernel/BridgeHost boundary. The result is a versioned age-encrypted file, a read-only `SecretSource` backed by that file, safe owner tooling for provisioning and rotation, and environment-aware startup behavior that fails closed when staging or production cannot load the configured vault. This plan closes the secret-source gap without pretending that bridge lifecycle execution is complete.

## 2. Scope
Add the encrypted vault implementation to the existing `bridge-host` boundary, use a pinned reviewed `age` dependency, expose a small `hydra-vault` provisioning binary that never prints secret values, add `HYDRA_VAULT_PATH` configuration, load the vault in the real kernel runtime, and pass the resulting source to the runtime bridge boundary. Add tests for round trips, wrong keys, tampering, atomic writes, secret-name handling, startup fail-closed behavior, and CLI output hygiene. Update the environment, deployment, security, command, and ignore documentation so the contract is operationally truthful.

## 3. Non-goals
No bridge deploy, pause, resume, sync, or adapter execution handler is added here; those capabilities remain unavailable until a separate governed lifecycle plan proves durable runtime behavior. No Nexus model/A2A/skills work, production deployment, staging drill, real customer credential provisioning, SQL migration, direct vendor API path, Node/npm toolchain, or production database operation is authorized. No raw secret value may be returned by an API, event, log, test failure, or CLI command output.

## 4. Context and Orientation
`HYDRA_VAULT_KEY` is currently required and touched during kernel startup, but no persisted vault is read and `StaticSecretSource` is the only available implementation. `ARCHITECTURE.md` specifies a file-based age-encrypted vault with named grants, while `SPEC-005-auth-and-permissions.md` specifies `hydra vault set|get-names|rotate`. `BridgeHost` already enforces grant checks before calling `SecretSource`, so the new source must remain read-only, name-scoped, and inside the Wasmtime boundary. Staging and production must not silently boot with an empty or invalid secret source.

## 7. Interfaces and Contracts
`EncryptedVault::load(path, passphrase)` MUST decrypt only the age-encrypted file format, reject malformed/tampered input, and keep plaintext in memory only for the owning source. `EncryptedVault::save` MUST write atomically, restrict the file to owner-read/write permissions where the platform supports it, and never log values. Secret names MUST be non-empty, bounded, and restricted to the documented safe character set; duplicate names are deterministic errors. `VaultSecretSource` MUST implement the existing `bridge_host::SecretSource` trait and return only the requested named value; it MUST NOT expose enumeration through the adapter interface.

The `hydra-vault` binary MUST read `HYDRA_VAULT_PATH` and `HYDRA_VAULT_KEY`, accept `set <name>` values from stdin, print names only for `get-names`, and use `HYDRA_VAULT_NEXT_KEY` for `rotate`; it MUST never accept secret values as command-line arguments or print them. `HYDRA_VAULT_PATH` is additive configuration with a documented default for development. The kernel MAY use an empty development source when the default file is absent, but staging and production MUST fail startup if the path is absent, unreadable, malformed, or cannot be decrypted. The runtime inventory MUST distinguish a loaded vault from an unavailable bridge lifecycle handler.

The implementation MUST use an explicitly pinned `age` crate version whose license and dependency graph pass Hydra policy. It MUST preserve the existing Rust-first, six-layer, Store-only-SQL, Wasmtime/WIT-only-adapter, no-secret-logging, and no-LLM-in-Governor invariants. No new event or SQL schema is needed.

## 10. Validation and Acceptance
The plan is complete only when the age-encrypted file can be created, loaded, rotated, and atomically replaced without exposing plaintext; wrong keys, tampering, malformed files, invalid names, duplicate names, and unsafe CLI invocation fail deterministically; `VaultSecretSource` satisfies the existing trait; the real kernel constructs it in the configured environment; staging/prod fail closed when it is unavailable; development behavior is explicitly bounded; the CLI prints names/status only; all listed format, lint, security, dependency, Compose, integration, E2E, verifier, and state commands pass; and EP-010 remains honestly partial.

## 11. Idempotence and Recovery
Repeated `set` updates one named secret deterministically and uses atomic replacement; repeated `get-names` is read-only; failed writes leave the previous vault intact; rotation decrypts the old file before replacing it and leaves the old file untouched on failure. Tests use temporary directories and synthetic values only. A missing or invalid production vault stops the process before serving requests. No migration, purge, rollback of user data, or production deployment is used for recovery.

## 13. Surprises & Discoveries
- The repository documents an age-encrypted vault but has no age dependency or persisted source; the existing `ring` package is indirect through transport/auth dependencies and is not an acceptable basis for a new bridge-host contract without making it direct and reviewing the design.
- Bridge lifecycle remains explicitly unavailable in the current runtime inventory, so this plan must not mark it available merely because a vault can load.
- The first M5 E2E attempt compiled the required scenarios but failed before execution because `scripts/test-e2e.sh` did not export the isolated `DATABASE_URL`; this was corrected by mirroring the existing loopback validation in `scripts/test-integration.sh`.

## 15. Outcomes & Retrospective
EP-018 is complete for its local acceptance boundary. Hydra now uses a pinned age 0.11.1 encrypted named-secret document, rejects duplicate or malformed secret maps, writes owner-only files with atomic replacement on Unix and write-through replacement on Windows, exposes a read-only `VaultSecretSource`, and includes the stdin-only `hydra-vault` provisioning/rotation binary. The real kernel constructs the source before database/NATS startup; an absent development vault disables only bridge-secret capability, while missing, invalid, unreadable, or undecryptable staging/production vaults fail closed. Bridge lifecycle remains truthfully unavailable.

Observed evidence: bridge-host 9 tests, hydra-vault 1 test, kernel vault/runtime 17 tests, full integration and failure suites, both required fake-Nexus E2E scenarios, preflight, formatting, lint, typecheck, security, dependency, Compose, cache-hit, and full verification all passed. The first integration attempt exposed zero free disk and the first E2E attempt exposed an unexported `DATABASE_URL`; both failures were preserved and corrected through bounded, non-masking recovery. No production deployment, push, merge, tag, or production database operation occurred.

Remaining risks are outside this plan: owner key custody, encrypted-vault backup/restore drill, real staging IdP/TLS, operational observability and recovery drills, performance/accessibility evidence, SBOM/provenance, human sign-off, and governed bridge lifecycle handlers remain EP-010 or future-plan work. These gaps keep Hydra from being declared production-ready.
